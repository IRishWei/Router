# Ticket 衔接与执行边界

2026-10-07 核对 GitHub #2—#25：24 张票的正文与本地发布快照一致，36 条原生阻塞关系一致且无环。T01/#2、T02/#3、T04/#5 已通过各自验收并关闭，当前前沿为 T03/#4；ready-for-agent 不表示前置已完成。

## 共享契约

| 契约 | 首次建立 | 后续使用 | 必须保持的行为 |
| --- | --- | --- | --- |
| 任务身份与请求身份 | T01—T03 | T16—T23 | 补充、重试、咨询、接管与预算扩展沿用任务；每次调用单独归属。 |
| Host 状态与配置快照 | T01—T02 | T08、T17—T19 | UI 发命令，Host 持久化；一个请求使用一个快照，稳定边界才应用修改。 |
| 最终模型选择 | T01 | T02、T12、T17—T18 | 真实请求、请求日志和界面一致；不改全局默认。 |
| 连接身份 | T02 | T05—T11 | 模型标识包含连接与计费来源；目录发现、授权和推理验证分别记录。 |
| 预算预留与结算 | T03 | 全部模型调用 | 判断、执行、咨询、评审、重试和重做走同一入口；失败未知用量不记零。 |
| 验收证据 | T13 | T14—T23 | 执行状态与通过/失败/无法确认分离；不完整覆盖不能自动通过。 |
| 可移植上下文 | T16—T17 | T18 | 咨询发送局部问题；接管保留完整对话、约束和工具记录，不静默截断。 |
| 效果许可 | T20—T21 | T23—T24 | Issue 完成、模拟通过和允许真实试用/发布是不同状态。 |

账号撤销或断开需在每次新调用前检查；旧快照不能授权继续开请求。请求已经发出时不能静默更换身份。

配置快照与当前资格复查是两个约束：稳定组装保存模型和版本，进入宿主流派发边界时同步复查启用/撤销状态；资格失效只能暂停，不临时换模型。预算等待尚未开始流派发，释放等待后必须再次检查。已进入流的调用继续保留原快照，新限制在后续调用检查。原生同 step 重试不重新组装 prompt，继续已捕获的模型配置；配置变更待下一完整组装、已完成工具结果后的稳定边界应用，每次重试仍需当前资格复查。

预算等待必须保留宿主的取消 signal。目标 rc.2 可在请求 waterfall 返回前等待，扩展预算后释放等待并继续同一 turn/step；取消则会写入 aborted 的 turn/end，没有公开的原 turn 恢复 API。T03 不能把取消冒充预算等待；T18 如跨取消或重启恢复，必须显式将新的宿主 turn 绑定到原 Router taskId，不能只复用旧内存 promise。原生 steer 补充在 next-step 进入当前 turn，queue/followup 则进入 next-turn，记录归属按实际已准入消息判定。

手动固定时，自动起始替换、接管、故障替换及策略试用均不得改变执行模型。跨模型咨询/评审在后续票实现时需要明确的协作开关；默认不绕过固定选择。

价格、预算和账本按完整 connectionId/accountId/billingPath/provider/model 身份归属，不能仅按 model 字符串合并。价格版本与单次 Call 快照一起保留；缺价、缺用量不推零，API 费用与订阅参考价值、不同币种分别呈现。T05/T06 的提供商内部透明 HTTP 重试需另行证明每个 attempt 有界且可记账，T03 的宿主 loop retry 测试不能替代该证明。

T04 已实际验证旧 oh-my-dsh 原包在目标 Desktop 被官方 CLI 与公开 PluginManager 拒绝，无豁免、激活或模型调用。复用决定是继续验证自研候选差异，局部参考咨询形状/纯规则，优先采用各接入票验证过的宿主组件；不移植伪 header、私有流包装、旧 preset 或普通 secret 投影。原包任务及效果未验证，T21 若缺少可比社区基线需明确 baseline unavailable，不把它的失败当作获胜。

5% 初始试用限制应控制实际合格任务比例并持久化计数，不能仅采用 5% 随机概率。实验充分性政策需在实验冻结前版本化；不能临时挑选门槛。

## 目标宿主的选择边界

目标为 Windows DSH Desktop 0.2.0-rc.2，安装包 build `04f392c9ddd144fa426da2045178797da6db6c11`，内置 Cordis 4.0.4，Host protocol 4。T01 已完成本目标的真实运行验证，证据见 `t01-host-evidence.md`；新增路由行为仍需各票独立验证。

`agent/request` waterfall 位于 `llm.prepareCall()` 和持久化 `request/header` 之前，是应用 provider/model 选择的公开边界。`llm/stream` 已绑定适配器及完整请求配置；在该事件临时替换模型会造成配置不匹配。T01 必须验证真实请求、持久化日志、session 展示之间的协同，再确定后续路由使用的入口。

不要将虚拟 Router provider 选择与真实 provider 请求混用：原生 pending 只由实际匹配的 request/header 事件消费，虚拟选择会导致界面仍显示虚拟模型及重复切换提示。后续自动路由使用真实 provider/model；没有 pending 时，原生选择从最新请求头读取，有手动 pending 时先完整尊重。T02 实测补充：再次手动选择刚完成的同一路由时，宿主可能省略相同 header 事件，pending 因而保留；不能保证每次匹配调用都会消费。此时继续尊重 pending；与固定或池资格冲突则明确暂停，用户通过原生选择器选不同的有效目标、实际发出新 header 后可恢复。T12/T17/T18 不得忽略残留 pending、伪造 header 或写私有缓存来自动跨模型。请求头之后的一致性不证明本步提示词已经一致；提示词变量、切换通知和请求必须使用同一稳定边界快照，并通过实际 controller 验证。原生 `selectModel` 会保存部署默认，因此不能作为自动切换的捷径。
